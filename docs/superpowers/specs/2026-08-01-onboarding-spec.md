# ⑤ 초기 설정(온보딩) — 확정 스펙

작성일: 2026-08-01 · 상태: 결정 확정 (미구현) · 선행: `2026-07-29-session-link-design.md`(②), `2026-07-30-session-mapping-spec.md`(②)

②가 확정한 것 중 이 문서가 올라서는 것: 세션 식별은 훅 stdin `session_id`, 주입 블록은 `app/services/session_link.py` 가 조립하고 `render_context()` 하나가 갈래를 고름. 이 문서는 그 갈래를 하나 늘린다.

## (a) 해결하려는 문제

1. **첫 실행이 빈 화면이다.** DB 를 만들면 카테고리 6개만 시드되고 워크스페이스는 0개다. 워크스페이스가 없으면 `unclassified` 블록의 "진행 중 워크스페이스: (없음)" 이 매 세션 주입되고, 세션은 카테고리만 찍고 끝난다. 대시보드의 4계층 중 위 두 층이 비어 있는 상태로 계속 굴러간다.
2. **채우는 방법이 사용자 머릿속에만 있다.** 워크스페이스를 만들려면 `add-workspace` 를 손으로 여러 번 쳐야 하는데, 무엇을 만들어야 하는지는 지난 몇 주의 작업 기억에서 나온다. 도구가 그 기억을 대신 읽어줄 수 있는데 아무도 시키지 않는다.
3. **히스토리는 이미 로컬에 있다.** `~/.claude/projects/*/*.jsonl` 에 프로젝트 44개 · 최근 14일 세션 141건(439MB)이 쌓여 있다. 여기서 "무슨 일을 하고 있었는지" 는 읽을 수 있지만, 셸은 그 내용을 이해할 수 없다(②가 분류를 훅이 못 하는 이유와 같음).
4. **한 번 거절한 사용자를 계속 붙잡으면 안 된다.** 자동 분류를 원하지 않는 사용자에게 매 세션 같은 질문이 주입되면 그 자체가 오염이다.

## (b) 확정한 결정

### D1. 온보딩은 Claude 세션이 진행한다. 웹·CLI 는 진입점을 만들지 않는다

훅이 `state="onboarding"` 블록을 주입하고, Claude 가 그 지시대로 질문·스캔·제안·등록을 수행한다.

근거 — 히스토리 분류는 대화 내용을 이해해야 하므로 LLM 만 할 수 있다. 웹 UI 에 7/14/안함 선택 화면을 만들어도 선택값을 `meta` 에 저장하는 것 이상은 못 하고, 실제 분류는 결국 다음 Claude 세션이 한다. 화면 하나를 늘려 왕복을 두 단계로 쪼개는 대신 질문 주체와 분류 주체를 한 곳에 둔다. ②에서 세션 분류를 같은 이유로 훅이 아닌 Claude 에게 넘긴 것과 같은 판단이다.

### D2. 트리거 조건은 "워크스페이스 0행 AND 거절 플래그 없음". 완료 플래그는 만들지 않는다

```text
workspaces 0행  AND  meta.onboarding_declined 없음   → state="onboarding"
브랜치 Jira = 워크스페이스의 jira_id                 → state="classified"   (기존)
그 외                                                → state="unclassified" (기존)
```

`meta` 에 넣는 키는 `onboarding_declined` 하나다. 완료를 기록하는 키는 두지 않는다 — 온보딩이 끝나면 워크스페이스가 최소 1개 생기므로 첫 조건이 저절로 깨진다. 상태를 두 곳(플래그와 실제 데이터)에 적으면 어긋날 수 있고, 어긋났을 때 신뢰해야 하는 쪽은 언제나 실제 데이터다.

부작용으로 **워크스페이스를 전부 지우면 온보딩이 다시 뜬다.** 이는 버그가 아니라 의도다 — 그 상태는 문제 1 과 구분되지 않는다. 다시 뜨는 게 싫은 사용자는 그때 "안 함" 을 고르면 플래그가 박힌다.

### D3. 히스토리는 CLI 가 압축하고 Claude 는 압축본만 읽는다

```bash
python3 dash.py scan-history --days 7
```

439MB 를 세션에 넣을 방법은 없다. CLI 가 먼저 요약해서 뱉고 Claude 는 그 stdout 만 읽는다.

| 항목 | 값 |
| --- | --- |
| 대상 | `~/.claude/projects/*/*.jsonl` 전체 (현재 프로젝트로 좁히지 않음) |
| 기간 필터 | 파일 mtime 이 `--days` 이내 |
| 파일당 읽는 양 | **앞 64KB만** (`head`) |
| 뽑는 값 | 프로젝트 폴더명 · 세션 시작 날짜 · 첫 사용자 발화 200자 · 사용자 발화 수 |
| 출력 크기 | 세션당 1줄. 14일 기준 약 141줄 |

전체 프로젝트를 보는 근거 — 카테고리와 워크스페이스는 저장소 경계와 무관한 전역 개념이다. 현재 프로젝트로 좁히면 `work-dashboard` 밖의 작업이 전부 누락되어 분류의 의미가 없어진다.

앞 64KB 인 근거 — 세션이 무엇에 관한 것인지는 **첫 지시**에 거의 다 들어 있다. 뒤로 갈수록 도구 결과가 쌓여 용량만 늘고 정보 밀도는 떨어진다. 기존 `transcript.recent()` 가 꼬리를 읽는 것과 방향이 반대이므로 `tail()` 옆에 `head()` 를 추가한다. `parse_line()` 은 그대로 재사용한다(도구 호출·사고 블록·훅 주입 제거 규칙이 이미 들어 있음).

### D4. 잔챙이 하한선 — 세션 2건 이하 묶음은 워크스페이스로 만들지 않는다

스캔 결과를 묶었을 때 세션 2건 이하인 묶음은 워크스페이스 후보에서 뺀다. 확인 트리 맨 아래에 `(기타: 세션 N건 — 워크스페이스 미생성)` 한 줄로만 표시한다.

근거 — 4단계 확인 트리는 사람이 한 화면에서 검수하는 자리다. 하한선이 없으면 141세션에서 워크스페이스 20개 이상이 제안되고, 그중 대부분은 한 번 묻고 끝난 단발 질문이다. 검수 비용이 온보딩의 이득을 넘어서면 사용자는 트리를 읽지 않고 승인하게 되고, 그 순간 이 기능은 쓰레기를 생성하는 장치가 된다.

임계값 `ONBOARDING_MIN_SESSIONS = 3`(= 2건 이하 제외)은 `app/constants.py` 에 둔다.

**하한선을 적용하는 주체는 Claude 다, 코드가 아니다.** 묶음은 의미 판단이므로 CLI 가 만들 수 없다 — `scan-history` 는 세션을 프로젝트 폴더별로만 정렬해 뱉고, 같은 일감끼리 묶는 것과 하한선을 적용하는 것은 주입 블록의 지시를 받은 Claude 가 한다. 상수를 `constants.py` 에 두는 이유는 블록 문장을 그 값에서 만들기 위해서다(숫자를 문장에 직접 박지 않는다).

### D4-1. 묶는 단위는 작업 위치(디렉토리) 하나 = 워크스페이스 하나

한 저장소 안의 기획·구현·배포는 워크스페이스로 쪼개지 않고 **착수 순서대로 놓는 할일**로 본다. 홈 디렉토리나 scratch 성격의 위치처럼 서로 무관한 일이 섞인 곳만 내용으로 다시 쪼갠다.

근거 — 2026-08-01 첫 실행에서 확인된 것이다. `scan-history` 출력이 이미 `cwd` 로 묶여 나오는데, 그 안을 첫 지시의 내용 유사도로 다시 쪼개자 한 서비스가 워크스페이스 4개로 갈라졌다. 이것이 틀린 이유는 두 가지다.

1. README 규칙이 "우선순위는 워크스페이스 순위 + 할일 순서로만 표현하고, 할일은 착수 가능한 순서로 놓는다" 이다. 기획 → 콘텐츠 → UI → 배포는 정확히 착수 가능한 순서이므로 할일의 모양이지 워크스페이스의 모양이 아니다.
2. `classified` 블록은 워크스페이스 **하나**의 배경·목적을 주입한다. 같은 저장소에서 도는 세션이 4개 중 어디에 붙느냐로 갈리면 주입 내용만 오락가락한다.

### D5. 카테고리는 두 안을 제시하고 고르게 한다. 삭제는 제안하지 않는다

```text
A. 디폴트(지금 있는 것): 개발 / 운영 / 장애 대응 / 개발환경 개선 / 스킬 개발 / 프로세스 개선
B. 히스토리 기반 제안:   (스캔 결과에서 도출한 목록)
```

선택지는 A · B 둘이다. A 를 고르면 아무것도 바꾸지 않고, B 를 고르면 **B 에만 있는 것을 `add-category` 로 추가**한다. 어느 쪽이든 기존 카테고리를 **지우지 않으며**, 이 사실을 질문할 때 함께 알린다 — "B 로 가도 기존 6개는 남습니다. 뺄 것이 있으면 말씀해주세요." 사용자가 특정 항목을 지목해 빼달라고 하면 그때만 지운다.

근거 — 시드 6개는 `categories_seeded` 플래그가 지키고 있고(지운 카테고리가 되살아나면 안 된다는 기존 규칙), 온보딩이 그것을 뒤집을 이유가 없다. 최근 7~14일에 안 나타났다는 사실은 그 카테고리가 불필요하다는 증거가 아니다 — 분기에 한 번 하는 일일 수도 있다. 삭제는 사용자가 카테고리 관리 화면에서 직접 한다.

### D6. 워크스페이스는 이름 + 목표만 먼저 만든다. 나머지는 별도 질문

`add-workspace` 로 `name` 과 `goal` 만 채우고 `background` · `purpose` · `considerations` 는 비운다. 등록 후 따로 묻는다.

```text
배경·목적·고려사항도 채울까요?
  1. 아니요 — 나중에 직접 채웁니다
  2. 네, 순차 — 워크스페이스 하나씩 채우고 확인받고 다음으로
  3. 네, 병렬 — 전부 추정해 한 번에 보여주고 한 번만 확인
```

근거 — 이름과 목표는 첫 발화에서 거의 그대로 읽히지만, 배경·목적·고려사항은 추정이다. 틀린 추정은 지워지지 않고 `classified` 블록에 매 세션 주입되어 계속 세션을 잘못된 방향으로 민다. 그래서 기본값은 "안 채움" 이고, 채울 때도 **순차 확인이 기본 동작**이다. 병렬은 사용자가 속도를 명시적으로 고를 때만 쓴다.

2(순차)는 워크스페이스 하나를 채우고 → 보여주고 → 승인받고 → 다음으로 간다. 3(병렬)은 전부 추정해 한 번에 보여주고 한 번만 승인받는다. 3 에서도 서브에이전트를 띄우지 않는다 — 한 응답에 전부 추정하는 것으로 충분히 빠르고, 에이전트를 띄우면 각자가 히스토리를 다시 읽어야 한다.

### D6-1. 어느 필드에 무엇을 넣는가 — 기준은 "매 세션 주입돼도 값어치가 있는가"

| 필드 | 넣는 것 | 안 넣는 것 |
| --- | --- | --- |
| 배경 | 왜 이 일이 존재하는가. 도메인의 문제. 시간이 지나도 안 변함 | 기술 스택, URL, 포트, 저장소 주소 |
| 목적 | 그 문제 중 무엇을 어떤 방향으로 푸는가 | 완료 조건 |
| 목표 | 끝났다고 판정할 수 있는 상태 | 방향·이유 |
| 고려사항 | 범위를 벗어나면 안 되는 제약·금지 | 구현 디테일, 일시적 이슈 |
| 할일 `note` | 그 할일 하나를 착수할 때만 필요한 구체 정보 | 워크스페이스 전체에 걸린 것 |

근거 — 이것도 첫 실행에서 나왔다. 초안이 배경에 Supabase·Expo·GitHub 주소·심사 대기 상태를 담고 고려사항에 "저녁 기준 18시" 같은 구현 디테일을 담자, 워크스페이스 컨텍스트와 할일 컨텍스트가 섞여 둘 다 못 쓰게 됐다. 워크스페이스 필드는 **매 세션 주입**되고 `note` 는 **착수 시점에만** 읽히므로(②의 설계), 주입 비용을 감당할 값어치가 없는 것은 전부 `note` 로 내려야 한다. 심사 대기처럼 곧 변하는 상태는 어느 쪽에도 넣지 않는다.

### D6-2. 할일까지 만든다. 상태도 추정해서 넣는다 (2026-08-01 결정 번복)

초안은 (c)에서 "할일 자동 생성 안 함 — 워크스페이스까지만" 으로 정했다. 근거는 "끝난 세션의 히스토리에서 착수 가능한 순서를 복원할 수 없다" 였다. **이 결정을 뒤집는다.**

번복 근거 — 첫 실행 직후 사용자가 "DB에 등록한 거 맞아? 안 보이는데" 라고 했다. 등록은 정상이었고, `app/services/board.py:29` 가 원인이었다.

```python
todos = _with_subtasks(con, todo_repo.list_by_workspace(con, workspace["id"]))
if not todos:
    continue      # 할일이 0개인 워크스페이스는 보드에서 통째로 빠진다
```

카테고리 그룹(`board.py:54`)도 같다. 즉 **워크스페이스만 만드는 온보딩은 화면에 아무것도 남기지 않는다.** 사용자에게는 초기 설정이 실패한 것과 구분되지 않는다. 원래 근거였던 "순서를 복원할 수 없다" 는 여전히 참이지만, 틀린 순서는 보드에서 끌어 옮기면 되고 틀린 상태는 클릭 한 번이다. 아무것도 안 보이는 것보다 싸다.

상태(`todo`/`doing`/`done`)도 함께 추정한다. 같은 이유다 — 전부 `todo` 로 두면 이미 끝낸 일이 남은 일로 보여 우선순위 판단을 흐린다.

`board.py` 를 고쳐 빈 워크스페이스를 보이게 하는 방법도 있었지만 택하지 않았다. 할일 없는 워크스페이스가 보드를 채우는 것은 온보딩과 무관하게 원래 원치 않는 동작이고, 온보딩의 산출물이 빈 껍데기인 편이 더 나쁘다.

### D7. 확인 트리 형식

```text
개발/
├── work-dashboard 세션 연동          세션 12건 (7/29~8/1)
│   목표: 훅으로 세션을 워크스페이스에 자동 연결
└── routex 항공 검색                  세션 5건 (7/28~7/30)
    목표: 항공권 검색 스킬 응답 정확도 개선
운영/
└── 배포 파이프라인 점검              세션 3건 (7/29~7/31)
    목표: ...
(기타: 세션 41건 — 워크스페이스 미생성)
```

트리를 보여주고 "이대로 진행 / 고칠 것을 알려주세요" 로 받는다. 자유 서술 수정을 반복하고, 확정된 뒤에만 DB 에 쓴다. 항목별 y/n 을 돌지 않는다 — 20개를 하나씩 묻는 것이 D4 가 피하려는 바로 그 비용이다.

## (c) 안 하는 것

- **웹 UI 온보딩 화면** — D1. 진입점을 늘리지 않는다.
- **과거 세션의 소급 연결** — 스캔에 쓴 세션들을 `sessions` 테이블에 넣거나 워크스페이스에 붙이지 않는다. 이미 끝난 세션이고, `sessions` 는 살아 있는 세션을 보는 곳이다.
- **`--days` 임의 값** — 7 · 14 두 개와 "안 함" 만. 자유 입력은 받되 안내는 세 갈래로 한다.
- **재실행 명령** — 온보딩을 다시 돌리는 `dash.py onboard --rerun` 을 만들지 않는다. 워크스페이스가 이미 있는 상태에서 필요한 것은 온보딩이 아니라 `add-workspace` 다.
