# ⑥ 선제조건 대기 상태 — 확정 스펙

작성일: 2026-08-03 · 상태: 결정 확정 (미구현)
선행: 없음 (①의 상태 집합을 늘리는 변경) · 후속: `2026-07-30-autorun-spec.md`(④) — ④는 이 상태를 착수 게이트로 씀

착수 순서에서 ④보다 앞임. ⑥ 없이 ④를 켜면 tick 이 조건 미충족 할일을 집고, 자율 세션은 "조건이 안 풀렸다"를 남길 자리가 없음.

## (a) 해결하려는 문제

1. **조건 텍스트는 있는데 상태가 없음.** `todos.precondition`·`subtasks.precondition` 은 이미 있지만, 지금 되는 할일과 조건이 안 풀린 할일이 보드에서 똑같은 `todo` 로 보임. 구분하려면 조건 문장을 읽어야 함.
2. **`next` 가 지금 못 하는 일을 내밈.** `planning._first_open` 은 `status != 'done'` 만 보므로 조건 미충족 할일이 1순위로 뽑힘. 한 번 그러면 그 줄 자체를 믿지 않게 됨.
3. **①이 ④로 미뤄둔 판단의 차례가 옴.** ①은 "순위는 실행 가능한 순서로 매긴다"를 규약으로 두고, 규약에 강제력이 없어 순서를 잘못 매기면 ④가 못 하는 일을 집는다고 적으며 의존성 표현의 필요를 ④ 시점으로 미뤘음. 지금이 그 자리임.
4. **자율 세션에는 "조건 미충족이니 사용자에게 알린다"의 상대가 없음.** 현재 주입 지침은 사람이 앞에 있는 세션만 전제함.

## (b) 확정한 결정

### D1. 할일 상태 값을 하나 늘림 — `waiting`

```python
TODO_STATUSES = ("todo", "waiting", "doing", "done")
STATUS_TODO, STATUS_WAITING, STATUS_DOING, STATUS_DONE = TODO_STATUSES
```

기존 3-튜플 언패킹 한 줄이 그대로 깨지므로 같이 고침. DB 스키마는 그대로 — `status` 는 TEXT 이고 검증이 상수에 있어 마이그레이션이 없음.

역할 분리를 못박음 — **`precondition` = 무엇을 기다리는가(자연어), `status` = 지금 착수 가능한가(판정 결과)**. 조건 문장이 붙어 있어도 충족됐으면 `todo` 다. 두 값이 같은 것을 표현하지 않음.

근거 — ④ D5 는 원래 4번째 상태를 만들지 않고 `autorun_runs.outcome='blocked'` 로만 기록하기로 했음(웹 UI·CLI·정렬이 다 따라 움직이는 비용). 이 결정을 뒤집음: 대기를 **보드에서 구분해 보는 것 자체가 목적**이고, 실행 기록에만 남기면 사람 화면에 나타나지 않아 목적을 달성하지 못함. 늘어나는 비용은 (d) 의 파일 목록 그대로다.

하위할일은 `subtasks.update` 가 같은 `TODO_STATUSES` 로 검증하므로 자동으로 `waiting` 을 받음. 별도 처리 없음.

### D2. 전이는 사람·세션이 명시적으로. 자동 판정 없음

조건은 자연어 문장이라 코드가 충족 여부를 판정할 수 없음. 판정 주체는 사람 또는 그 조건을 읽은 세션임.

| 경로 | 방법 |
| --- | --- |
| CLI | `dash.py set-status todo <id> waiting` / `… todo` |
| 보드 | 할일 케밥 메뉴 `대기로 내리기` / `대기 해제` |

상태 순환 버튼(`todo → doing → done`)에는 넣지 않음 — 클릭마다 대기를 지나가면 3-스텝 순환의 값이 사라짐. `completed_at` 은 `done` 전환에서만 찍히므로 이 상태와 무관.

### D3. `next` 후보에서 제외

`planning._first_open` 의 조건을 `status != 'done'` → `status in ('todo', 'doing')` 으로 바꿈.

| 상황 | 결과 |
| --- | --- |
| 워크스페이스에 `waiting` 과 `todo` 가 섞임 | `waiting` 을 건너뛰고 그다음 `todo` 를 뽑음 |
| 워크스페이스의 미완료가 전부 `waiting` | 그 워크스페이스를 건너뛰고 다음 워크스페이스로 |
| 모든 후보가 `waiting` | `next` 없음 — 사람이 조건을 풀어야 진행됨 |

사람용 `next` 와 ④의 후보 선정이 같은 함수를 계속 공유함(④ D1).

### D4. 보드 표시 — 숨기지 않고 흐리게, 조건은 항상 한 줄

- 카드 위치와 정렬은 그대로(`sort_order` 유지). 대기를 아래로 밀면 ①의 "선행 위, 후행 아래" 규약이 깨져 순서가 실행 순서를 뜻하지 않게 됨
- 상태 칩에 `대기` 를 표시하고 행 전체를 딤 처리
- 조건 첫 줄을 제목 아래에 **항상** 노출(접지 않음). 대기의 이유가 보이지 않으면 상태만 보고 무엇을 기다리는지 다시 열어봐야 함
- `완료 항목 표시` 체크박스와 무관하게 늘 보임 — 대기는 끝난 일이 아니라 막힌 일이므로 숨기면 존재를 잊음
- 워크스페이스 헤더에 대기 건수는 붙이지 않음. 숫자를 하나 더 늘려 얻는 것이 없음

### D5. 주입 블록 표기

`session_link` 의 할일 줄에 `[대기]` 를 붙이고 조건 한 줄을 함께 실음. 지침 문장은 현재의 "'조건:' 이 붙은 할일은 그 조건이 충족됐는지 먼저 확인하고, 미충족이면 착수하지 않고 사용자에게 알린다" 를 아래로 교체함.

> 상태가 `[대기]` 인 할일은 착수하지 않는다. 조건이 풀렸다고 판단되면 `dash.py set-status todo <id> todo` 로 올린 뒤 착수한다. 조건이 안 풀렸으면 그 사실만 알리고 다음 할일로 넘어간다.

## (c) 의도적으로 안 하는 것

- 조건 충족 자동 판정 — 자연어 조건이라 코드가 못 함 (D2)
- `blocked_by` 같은 할일 간 의존성 필드 — 순서 규약(`sort_order`)과 두 곳에서 같은 것을 표현하게 됨. 대기 상태 하나로 "지금 되는가"만 표현함
- 워크스페이스 상태에 대기 추가 — `active`/`paused` 로 이미 표현됨
- 대기 사유 이력·대기 기간 통계
- 조건이 풀렸는지 감시하는 주체 — 보는 사람이 판단함. 감시를 만들면 조건 문장을 기계가 읽어야 함

**건드리지 않음** — DB 스키마(값만 늘어남, 마이그레이션 불필요), `app/repositories/todos.py`·`subtasks.py` 의 검증 로직(상수를 그대로 읽으므로 코드 변경 없음), `app/services/board.py` 의 `done_count`, `sessions`·`decisions`·`autorun_*` 계열.

**착수 전 확인** — `constants.py`·`static/*` 는 다른 세션이 동시에 고칠 수 있음. `git status`·`git log` 로 확인 후 착수.

## 검증

`python3 -m tests` 에 합류.

1. `set-status todo <id> waiting` → 상태 저장, `completed_at` 은 NULL 유지
2. `waiting` 할일은 `next` 후보에서 빠지고 같은 워크스페이스의 다음 `todo` 가 뽑힘
3. 워크스페이스의 미완료가 전부 `waiting` → 그 워크스페이스를 건너뛰고 다음 워크스페이스
4. 모든 후보가 `waiting` → `next` 가 없음
5. 하위할일도 `waiting` 을 받고, 범위 밖 값은 에러
6. 주입 블록에 `[대기]` 와 조건 한 줄이 실림
7. `waiting` → `todo` 로 올린 뒤 `next` 가 다시 그 할일을 집음
8. `GET /api/tree` 응답에 상태가 그대로 실려 프런트가 딤 처리할 수 있음

수동 확인 — 보드에서 대기 할일이 `완료 항목 표시` 와 무관하게 보이는지, 조건 줄이 접히지 않는지, 상태 순환 버튼이 대기를 지나가지 않는지.
